# Learning log

One entry per phase: what to understand before the interview, why it matters, and where to read more. Each entry points at the place in this repo where the idea shows up.

## Phase 0 — Setup

### What I should learn here

- **Expo is now the default way to start a React Native app.** In 2018 the choice was "Expo (limited) or bare React Native (full control)". That split is gone: the React Native docs tell you to use a framework, and Expo is the one they name. You keep full native access, because the app is a normal native project that Expo generates and builds. "Bare" now only means "I maintain `ios/` and `android/` by hand".
  Here: [apps/mobile/package.json](../apps/mobile/package.json) — `main` is `expo-router/entry`; there is no `index.js` or `AppRegistry` call.
  Read: [React Native: get started](https://reactnative.dev/docs/environment-setup), [Expo: core concepts](https://docs.expo.dev/workflow/overview/).

- **Expo Go vs development builds.** Expo Go is a prebuilt app from the store with a fixed set of native modules. It is fine for a first demo, but it cannot load a native library it does not already contain. A development build is _your own_ app (your bundle id, your native modules) with the `expo-dev-client` launcher and dev menu added. Pantry needs one from day one because MMKV, Unistyles and the on-device AI module are not in Expo Go. The cost: the first `pnpm ios` compiles native code (minutes), and you rebuild whenever a native dependency changes. JS changes still hot-reload through Metro.
  Here: `expo-dev-client` in [apps/mobile/package.json](../apps/mobile/package.json); the `ios` script runs `expo run:ios`.
  Read: [Development builds](https://docs.expo.dev/develop/development-builds/introduction/).

- **Continuous Native Generation (CNG) and config plugins.** `ios/` and `android/` are build output, like `dist/` on the web. `expo prebuild` generates them from `app.config.ts` plus the config plugins of each library, so they are git-ignored. To change something native (a permission, the URL scheme, a build setting) you change the config or write a plugin; you do not open Xcode and edit a file. This is what makes React Native upgrades cheap: delete the folders and generate them again for the new version. Interview answer to "how do you upgrade RN?": bump the SDK, run `expo install --fix`, prebuild clean, fix what the changelog lists.
  Here: [apps/mobile/app.config.ts](../apps/mobile/app.config.ts) (bundle id, `pantry://` scheme, splash plugin); `apps/mobile/ios/` in [.gitignore](../.gitignore).
  Read: [Continuous Native Generation](https://docs.expo.dev/workflow/continuous-native-generation/), [Config plugins](https://docs.expo.dev/config-plugins/introduction/).

- **The New Architecture is the only architecture.** The old design sent JSON messages over an asynchronous _bridge_ between JS and native. It is removed. Now: **JSI** lets JS hold references to C++ objects and call them directly; **TurboModules** are native modules built on JSI (lazy-loaded, typed from a spec by Codegen, can be synchronous); **Fabric** is the new renderer, which can render synchronously and supports React's concurrent features (transitions, Suspense); **bridgeless mode** means the bridge is not even initialized. Why it matters in practice: synchronous storage (MMKV), animations and gestures that run on the UI thread, and React 19 features that work as they do on the web. Nothing in the app config turns it on, because there is nothing to turn off.
  Here: no flag to point at. The proof is in the build log: pods such as `React-Fabric` and `ReactCodegen` are compiled.
  Read: [About the New Architecture](https://reactnative.dev/architecture/landing-page), [Expo: New Architecture](https://docs.expo.dev/guides/new-architecture/).

- **Hermes is the JS engine.** Not JavaScriptCore, and not V8. Hermes compiles JS to bytecode _at build time_, so a release app does not parse and compile JS at startup. That lowers time-to-interactive and memory, mostly on mid-range Android. It also defines what "debugging" means now: React Native DevTools talks to Hermes directly over the Chrome DevTools Protocol. The old "Debug in Chrome" mode, which ran your JS in a different engine, is gone, and so is Flipper.
  Here: nothing to configure; `hermes-engine` is one of the pods. Performance numbers come in Phase 5.
  Read: [Using Hermes](https://reactnative.dev/docs/hermes), [Expo: tools for development](https://docs.expo.dev/develop/tools/).

- **AI-assisted development is part of the toolchain.** The Expo template now ships an `AGENTS.md` that says, in short, "Expo changes every release, read the versioned docs, do not answer from memory". This repo does the same with [CLAUDE.md](../CLAUDE.md): commands, folder rules, conventions and a fixed workflow (one task, one commit, checks before finishing). Expo also publishes its docs in an LLM-friendly index and has an MCP server that lets an agent search the docs and work with EAS. The senior-level point for an interview: the agent's output is only as good as the constraints and the checks around it, so the rules file, the typed schema, lint and tests are the real quality gate.
  Here: [CLAUDE.md](../CLAUDE.md), [docs/PLAN.md](PLAN.md), [.github/workflows/ci.yml](../.github/workflows/ci.yml).
  Read: [Expo docs index for LLMs](https://docs.expo.dev/llms.txt), [Expo MCP server](https://docs.expo.dev/eas/ai/mcp/).

### Also set up in this phase (short notes)

- **React Compiler is on** (`experiments.reactCompiler` in [app.config.ts](../apps/mobile/app.config.ts)). It memoizes components and hooks at build time, so the code has no `useMemo`, `useCallback` or `React.memo`. The ESLint rules from `eslint-plugin-react-hooks` report code the compiler cannot optimize. The ADR with measurements comes in Phase 5. Read: [React Compiler](https://react.dev/learn/react-compiler), [Expo: React Compiler](https://docs.expo.dev/guides/react-compiler/).
- **One schema, generated types.** [packages/shared/schema.graphql](../packages/shared/schema.graphql) is the contract. `pnpm codegen` turns each `.graphql` operation in the app into a typed document, and CI fails if the generated file is stale. Read: [Codegen client preset](https://the-guild.dev/graphql/codegen/plugins/presets/preset-client).
- **Monorepo.** Expo detects a pnpm workspace and configures Metro for it; there is no `metro.config.js`. pnpm blocks dependency install scripts unless they are listed under `allowBuilds` in [pnpm-workspace.yaml](../pnpm-workspace.yaml). Read: [Expo: monorepos](https://docs.expo.dev/guides/monorepos/), [pnpm settings](https://pnpm.io/settings).
- **Idempotency keys on cart mutations.** A mobile client retries after a lost response, so "add 2" could be applied twice. Each user action carries a key and the server applies a key once ([server/src/cart.ts](../server/src/cart.ts)). The offline queue in Phase 3 depends on this.

## Phase 1 — Shell and design system

### What I should learn here

- **Expo Router vs React Navigation.** Expo Router is not a different navigation engine: it is built on React Navigation and uses the same native stack and tab navigators with the same options. What changes is where the structure is declared. In 2018 you built nested navigators in code and wrote a separate linking config by hand. Now a file in `app/` is a route, a `_layout.tsx` is the navigator for its folder, and every screen has a URL without extra work, so deep links come for free. React Navigation 7 has closed part of the gap with its static configuration (typed, with automatic linking). Trade-off to say in an interview: file-based routing gives URLs, typed links and web support by default, but the folder tree _is_ the navigation tree, so unusual structures (a navigator chosen at runtime) are harder. One detail that bites on a cold-start deep link: without `unstable_settings.anchor`, `pantry://recipe/r1` opens the recipe with nothing under it, so there is no back button.
  Here: [app/\_layout.tsx](../apps/mobile/app/_layout.tsx) (stack, modal, `anchor`), [app/(tabs)/\_layout.tsx](<../apps/mobile/app/(tabs)/_layout.tsx>); route files only render a feature screen.
  Read: [Expo Router introduction](https://docs.expo.dev/router/introduction/), [React Navigation static configuration](https://reactnavigation.org/docs/static-configuration), [Linking into your app](https://docs.expo.dev/linking/into-your-app/).

- **Typed routes.** With `experiments.typedRoutes`, Expo generates a declaration file of every route (`.expo/types/router.d.ts`, git-ignored) when the dev server or typecheck runs. `router.push('/recipe/[id]')` without an `id`, or a link to a route that does not exist, is a compile error. Two limits: route params still arrive as strings at runtime, so anything structured (search filters in Phase 3) is parsed and validated with Zod; and the generated file is git-ignored, so on a fresh clone (CI) there are no route types and `tsc` fails. The mobile `typecheck` script therefore generates them first with `expo customize tsconfig.json`, the command the Expo docs give for CI.
  Here: `typedRoutes` in [app.config.ts](../apps/mobile/app.config.ts); [navigation.test.tsx](../apps/mobile/src/__tests__/navigation.test.tsx) and [deepLinks.test.tsx](../apps/mobile/src/__tests__/deepLinks.test.tsx) use the Expo Router testing library. Jest cannot parse a custom-scheme URL the way a device does, so those tests start at the path and `xcrun simctl openurl booted pantry://recipe/r1` was the manual check.
  Read: [Typed routes](https://docs.expo.dev/router/reference/typed-routes/), [Testing Expo Router](https://docs.expo.dev/router/reference/testing/).

- **Unistyles 3 and the Nitro layer.** Most theming libraries put the theme in React context, so a theme change re-renders every themed component. Unistyles 3 has a C++ core exposed to JS through **Nitro Modules** (Margelo's JSI-based framework for native modules, also used by MMKV). Its Babel plugin records which theme values and runtime values (insets, screen size) each style uses and links styles to native views; on a theme change the native side updates those views directly, with no React render. Costs that follow from this design: themes must be registered before any `StyleSheet.create` runs (hence the import order in the app entry); a third-party component (for example `SafeAreaView`) does not follow theme changes unless wrapped with `withUnistyles`; and in Jest there is no native side, so tests use a mock and re-render after switching theme. Know the landscape for Phase 6: TurboModules (React Native's own), Expo Modules API (Swift/Kotlin, what this repo will use), Nitro (fastest, C++/Swift/Kotlin hybrid objects).
  Here: [index.ts](../apps/mobile/index.ts) (import order), [src/design-system/unistyles.ts](../apps/mobile/src/design-system/unistyles.ts), the Babel plugin in [babel.config.js](../apps/mobile/babel.config.js), [src/test/unistyles.ts](../apps/mobile/src/test/unistyles.ts); [ADR 0002](adr/0002-styling-unistyles.md).
  Read: [How Unistyles works](https://www.unistyl.es/v3/start/how-unistyles-works), [Nitro Modules](https://nitro.margelo.com/).

- **Edge-to-edge and safe areas.** Android now draws apps behind the status bar and the navigation bar: Android 15 enforces it for apps that target API 35, and newer versions remove the opt-out. Expo turns it on by default, and Unistyles requires it. So "content under the system bars" is now the app's problem on both platforms, not only around the iPhone notch. The rule here: navigation headers and the tab bar handle their own edges; a screen pads the bottom with the inset only when nothing else covers it; the status bar style follows the **app's** theme, not the system's, because the user can pick dark mode while the phone is light. Verified on two iOS Simulator sizes; Android is not checked until task 5.1.
  Here: [Screen.tsx](../apps/mobile/src/design-system/primitives/Screen.tsx) (`rt.insets.bottom`), [ThemedStatusBar.tsx](../apps/mobile/src/design-system/primitives/ThemedStatusBar.tsx).
  Read: [Android edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge), [Expo: safe areas](https://docs.expo.dev/develop/user-interface/safe-areas/).

## Phase 2 — Data layer

### What I should learn here

- **The normalized cache and type policies.** Apollo does not store a query result as one blob. It splits the result into entities, each stored under `__typename:id` (`Product:p1`), and a query keeps references to them. So two screens that show the same product share one record: when a mutation or a second query changes it, every component that reads it updates, and nothing is fetched twice. The cache can only do this if it knows two things the schema does not say. First, **how to identify an entity**: the default `id` field works for us, so there are no `keyFields`. Second, **what a paginated field is**: `feed(first, after)` is one list, not one list per `after` value, so the field policy names its key arguments (none for `feed`; `input` for `search`, so "pasta" and "pasta, vegan" are two lists) and a `merge` function that appends a page, or replaces the list when there is no `after`. Two details worth saying in an interview: Apollo's `relayStylePagination()` does not drop duplicates when pages overlap (a row inserted on the server between two requests), and a duplicate row breaks list keys, so we wrote our own 40-line merge and tested it on its own; and unions (`CatalogItem = Product | Recipe`) need `possibleTypes` from the schema, or a fragment `... on Product` cannot be matched.
  Here: [typePolicies.ts](../apps/mobile/src/lib/apollo/typePolicies.ts), [pagination.ts](../apps/mobile/src/lib/apollo/pagination.ts), [pagination.test.ts](../apps/mobile/src/lib/apollo/__tests__/pagination.test.ts); [ADR 0007](adr/0007-apollo-cache-pagination-masking-persistence.md).
  Read: [Cache configuration](https://www.apollographql.com/docs/react/caching/cache-configuration), [Pagination: core API](https://www.apollographql.com/docs/react/pagination/core-api).

- **Data masking and colocated fragments (`useFragment`).** With masking on, a query result contains only the fields the query selects itself; the fields of a fragment spread are hidden behind a reference, and the component that owns the fragment reads them with `useFragment`. Two benefits. A component's data needs are local: removing a field from `ProductCardFields` can only break `ProductCard`, and TypeScript enforces it. Re-renders are scoped: `useFragment` subscribes to one entity's fields, so when `Product:p1` changes only its card re-renders, not the feed or the other rows. It also gave the details screens their "cached header at once" behavior for free: `RecipeHeaderFields` selects the same fields as the feed card, so for a recipe opened from the feed that fragment is already complete in the cache (`complete: true`) and the header renders with no request; after a deep link it is incomplete and a placeholder shows. Gotchas met here: a fragment that spreads another fragment has a document with two fragment definitions, so `useFragment` needs `fragmentName` or it throws; and a test server must return the _unmasked_ data (all fields), while the app's result types hide them.
  Here: [feed.graphql](../apps/mobile/src/features/catalog/api/feed.graphql), [ProductCard.tsx](../apps/mobile/src/features/catalog/components/ProductCard.tsx), [RecipeHeader.tsx](../apps/mobile/src/features/catalog/components/RecipeHeader.tsx), [IngredientList.tsx](../apps/mobile/src/features/catalog/components/IngredientList.tsx) (`fragmentName`).
  Read: [Fragments: data masking](https://www.apollographql.com/docs/react/data/fragments#data-masking), [`useFragment`](https://www.apollographql.com/docs/react/data/fragments#usefragment).

- **Fetch policies, and the `cache-and-network` trap.** `cache-first` (the default) never asks the server when the cache has the data, so a persisted cache would show the same list until the user refreshes. `cache-and-network` returns the cache at once and also asks the server, which is what an offline-capable feed wants. The trap: a query keeps its policy, so every later cache write (a page added by `fetchMore`) triggers another request for page one, which _replaces_ the list and throws away the pages the user scrolled to. The fix is `nextFetchPolicy: 'cache-first'`, which switches the policy after the first answer. A second consequence: while that first request runs, loading the next page is unsafe, because its answer would be overwritten, so the feed treats it as busy. And with no network, a failed background request must not replace the cached list with an error screen: the screen shows the list and, when the device is online, a notice.
  Here: [useFeed.ts](../apps/mobile/src/features/catalog/hooks/useFeed.ts), [offlineStart.test.tsx](../apps/mobile/src/features/catalog/__tests__/offlineStart.test.tsx); [ADR 0009](adr/0009-offline-start-network-status-and-feed-policy.md).
  Read: [Setting a fetch policy](https://www.apollographql.com/docs/react/data/queries#setting-a-fetch-policy).

- **FlashList v2 and recycling.** `FlatList` creates a row component when a row scrolls in and destroys it when it scrolls out; on a slow phone that shows as blank areas and dropped frames. FlashList keeps a small pool of mounted rows and _reuses_ them for new data. v2 was rewritten for the New Architecture and measures the rows itself, so the v1 `estimatedItemSize` is gone. Recycling has rules that are easy to get wrong. A row component keeps its local state when it is reused for another item, so rows must derive everything from props (ours read the cache by id with `useFragment`). Rows of different layouts need `getItemType` (products and recipes get separate pools). An image must know that it was recycled: without `recyclingKey` a reused row shows the previous item's photo until the new one loads. And `onEndReached` fires on every scroll event near the end, so the handler must be re-entrant safe: one request at a time, none after the last page, and no loop after a failure.
  Here: [HomeScreen.tsx](../apps/mobile/src/features/catalog/components/HomeScreen.tsx), [CatalogImage.tsx](../apps/mobile/src/features/catalog/components/CatalogImage.tsx), [feed.ts](../apps/mobile/src/features/catalog/model/feed.ts) (`canLoadMore`, `rowType`); [ADR 0003](adr/0003-list-library-flashlist.md).
  Read: [FlashList](https://shopify.github.io/flash-list/), [expo-image](https://docs.expo.dev/versions/latest/sdk/image/).

- **MMKV, JSI and a persisted cache.** MMKV is a key-value store from WeChat, exposed to JS through JSI (here through Nitro Modules). Its calls are _synchronous_: no `await`, no promise. With AsyncStorage, a persisted cache had to be restored asynchronously, so apps showed a splash screen or an empty first frame. With MMKV the cache is restored while the module loads, before the first render, so the first frame already has data, also offline. What we added around it: a debounced save (1 s, at most 5 s after the first unsaved write, because constant writes while scrolling would starve a plain debounce), a flush when the app goes to `inactive`/`background`, a 5 MB cap with an all-or-nothing purge (a part of a normalized cache has dangling references), and a version made of a format number and a schema hash, so an app update with a new schema drops the old cache. The price: restoring is `JSON.parse` on the JS thread at startup, which the cap bounds; the number is an assumption until Phase 5 measures it.
  Here: [appClient.ts](../apps/mobile/src/lib/apollo/appClient.ts), [cachePersistor.ts](../apps/mobile/src/lib/apollo/persistence/cachePersistor.ts), [mmkv.ts](../apps/mobile/src/lib/storage/mmkv.ts).
  Read: [react-native-mmkv](https://github.com/mrousavy/react-native-mmkv), [About the New Architecture](https://reactnative.dev/architecture/landing-page).

- **Suspense for data: what it is, and why this app does not use it (yet).** In React 19, a component can `use(promise)` or call a Suspense-enabled hook (Apollo's `useSuspenseQuery`); while the data is missing it _suspends_, and the nearest `<Suspense fallback>` shows a placeholder. The code then reads as if the data were always there, and loading and error states move out of the component into boundaries. We use `useQuery` with explicit states instead, for a concrete reason: our details screens have a third state that Suspense does not model well, "some of the data is in the cache, show it now and load the rest". With Suspense that needs nested boundaries or `returnPartialData`, while fragments make it a one-line check (`complete`). Where Suspense fits well: a screen that is all-or-nothing, and transitions (`useTransition`) that keep the old screen visible while the new one loads. Be ready to say this trade-off in both directions.
  Here: [RecipeScreen.tsx](../apps/mobile/src/features/catalog/components/RecipeScreen.tsx) (status from `detailsStatus`), [details.ts](../apps/mobile/src/features/catalog/model/details.ts).
  Read: [Suspense](https://react.dev/reference/react/Suspense), [`use`](https://react.dev/reference/react/use), [`useSuspenseQuery`](https://www.apollographql.com/docs/react/api/react/useSuspenseQuery).

- **Error boundaries.** Only a class component can be an error boundary, and it catches only errors thrown _while rendering_ (and in lifecycle methods): not event handlers, not async code. So there are two kinds of failure here, with two answers. A failed query is data: an inline `ErrorState` with a retry. A render error (a bug) goes to the boundary, which shows the same message and reports the error, while the tab bar and the other tabs keep working. A retry must _remount_ the subtree (a new `key`), or it would keep the state that broke it; a details screen also resets when the item id changes. A thing found while testing: React renders a failed tree a second time before it gives up on it, so an error that happens only once is invisible; the test error persists until the retry.
  Here: [ErrorBoundary.tsx](../apps/mobile/src/design-system/primitives/ErrorBoundary.tsx), [FeatureErrorBoundary.tsx](../apps/mobile/src/lib/error-boundary/FeatureErrorBoundary.tsx), [errorBoundaries.test.tsx](../apps/mobile/src/__tests__/errorBoundaries.test.tsx).
  Read: [Catching rendering errors with an error boundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).

- **Testing the data layer: RNTL + MSW.** The tests do not mock Apollo or the hooks. MSW answers at the network level, so the real link chain (retry, error link, parsing), the cache and the components all run, and a test says only what the server returns. Handlers are built from the generated documents, so a fixture that does not match the query does not compile. Things that were not obvious: MSW 3 is ES-module only and works at the socket level, and jest-expo replaces the global `fetch` with Expo's native one, so a custom Jest environment keeps Node's `fetch` for it ([ADR 0008](adr/0008-test-harness-msw-in-jest-expo.md)); a request with no handler fails the test instead of reaching a real server (it reached a developer's running server once); Expo Router's `renderRouter` turns on fake timers, and a network request does not finish while time is faked, so tests that need data render the component without the router and spy on `router.push`; and FlashList's own Jest layout (rows of 100 pt) makes the list look short and fire `onEndReached` on mount, so the tests use card-sized rows.
  Here: [src/test/](../apps/mobile/src/test/) (`render.tsx`, `msw/`, `flashlist.ts`, `network.ts`), [HomeScreen.test.tsx](../apps/mobile/src/features/catalog/__tests__/HomeScreen.test.tsx).
  Read: [MSW](https://mswjs.io/docs/), [React Native Testing Library](https://callstack.github.io/react-native-testing-library/).

### Also set up in this phase (short notes)

- **Network status.** `expo-network` reports connected / internet reachable; the app treats "connected but no internet" as offline and "no reading yet" as online (no banner flash at launch). It is a hint, not a promise: a failed request is handled whatever it says. Read: [expo-network](https://docs.expo.dev/versions/latest/sdk/network/).
- **Retries are limited on purpose.** Network errors and 5xx are retried (3 attempts, jittered backoff); 4xx and GraphQL errors are not, because the same request gives the same answer; mutations are retried only with an `idempotencyKey`. A request has a 15 s timeout, because React Native's `fetch` has none.
- **Details screens have four states, not two.** Loading, ready, not found (the server answered `null`: offer a way back, no retry) and error (retry). Not found is not an error, and the difference is a pure function with a table test ([details.ts](../apps/mobile/src/features/catalog/model/details.ts)).
- **Allergens are always shown,** also when there are none ("No listed allergens"), so a shopper who avoids one never has to guess whether the list is missing.
- **Plural forms are tested for every plural word,** not for one: EN needs `one` and `other`, PL needs `one`, `few`, `many` and `other` ([i18n.test.tsx](../apps/mobile/src/lib/i18n/__tests__/i18n.test.tsx)).
- **Not verified yet:** feed scroll smoothness and cold-start time on a release build (Phase 5), and anything on Android (task 5.1).

## Phase 3 — Search and cart

### What I should learn here

- **Reanimated 4 and worklets.** A _worklet_ is a JavaScript function that is copied to a second JS runtime that lives on the UI thread, so it can run every frame without waiting for the JS thread, which may be busy rendering a list. In Reanimated 4 the worklet machinery is its own package, `react-native-worklets` (it is in [package.json](../apps/mobile/package.json)), and Reanimated sits on top of it. Two ways to animate: **CSS-style animations** (`animationName`, durations, in a style object; no shared values, no worklet code) and **shared values with `useAnimatedStyle`** (a value that lives on the UI thread, and a style computed from it by a worklet). To go back from the UI thread to React you call `scheduleOnRN` (the old `runOnJS`): the swipeable row does it to tell JS that it opened. Be honest in an interview about what this repo does: it wrote **no worklet of its own**. The add-to-cart "pop" is a CSS animation, restarted by changing the element's `key`; the swipe uses Gesture Handler's `ReanimatedSwipeable`, whose pan handling and row movement are worklets. Reduced motion: Reanimated animations default to `ReduceMotion.System`, so they jump to the end when the OS asks; our own pop also checks `useReducedMotion()` and is not started at all.
  Here: [AddToCartButton.tsx](../apps/mobile/src/features/cart/components/AddToCartButton.tsx) (`ADDED_ANIMATION`), [SwipeToRemove.tsx](../apps/mobile/src/features/cart/components/SwipeToRemove.tsx), [Skeleton.tsx](../apps/mobile/src/design-system/primitives/Skeleton.tsx).

- **Gesture Handler 3.** Touches in React Native normally go through JS and the responder system; a gesture that must follow a finger at 60 or 120 fps cannot afford that. Gesture Handler recognizes gestures **natively** (a pan, a tap, a long press, with proper conflict rules between them and with scroll views) and sends events to worklets, so the view moves on the UI thread. Version 3 replaces the old `Gesture.Pan()` builder with **hooks** (`usePanGesture`, `useTapGesture`) used with a `GestureDetector`; the old API still exists under `Legacy…` names. Everything needs a `GestureHandlerRootView` at the top of the tree ([_layout.tsx](../apps/mobile/app/_layout.tsx)), and it is **native code**, so adding it needs a new development build, not a reload. Why `ReanimatedSwipeable` and not a hand-made pan: row swipes have many edge cases (a vertical scroll must win over a small sideways move, friction, thresholds, RTL, closing when another row opens), and the library's component handles them. A swipe is a shortcut here, never the only way: every row has a visible, labelled "Remove" button, and the swipe panel is hidden from screen readers because it would only repeat that button.
  Here: [SwipeToRemove.tsx](../apps/mobile/src/features/cart/components/SwipeToRemove.tsx), [CartLineRow.tsx](../apps/mobile/src/features/cart/components/CartLineRow.tsx).
  Read: [Gesture Handler: introduction](https://docs.swmansion.com/react-native-gesture-handler/docs/), [Reanimated Swipeable](https://docs.swmansion.com/react-native-gesture-handler/docs/components/reanimated-swipeable).

- **Optimistic UI, and why `useOptimistic` is not used here.** "Optimistic" means: show the result of an action before the server confirms, and undo it if the server refuses. React 19 has `useOptimistic(state, reducer)`: during an async transition the hook returns a temporary state, and when the transition ends it falls back to the real one, which is the rollback. Apollo has its own version, `optimisticResponse`, a fake result written into a temporary cache layer until the real one arrives. Both cover **one request in flight**. The cart needs more: the change must survive **offline**, a **restart**, and a **lost response**. So the optimistic layer is the persisted queue itself: the screen shows the server cart with the queued operations applied by a pure function, and a refused operation simply leaves the queue, which is the rollback. Every operation is an absolute quantity (`setCartQty`) with an idempotency key, so applying one twice gives the same cart. The things to be able to explain on a whiteboard: why a relative "add 1" is not safe to retry, why an operation that was sent is **frozen** (never merged or re-keyed, because it may have reached the server), why operations made offline are **not** sent as failing attempts (so they can still be merged), and what "last write wins across devices" costs.
  Here: [useCart.ts](../apps/mobile/src/features/cart/hooks/useCart.ts), [queue.ts](../apps/mobile/src/features/cart/model/queue.ts), [replayer.ts](../apps/mobile/src/features/cart/model/replayer.ts), [CartSync.tsx](../apps/mobile/src/features/cart/components/CartSync.tsx); [ADR 0013](adr/0013-offline-cart-queue.md), [ADR 0014](adr/0014-cart-ui-queue-projection-is-the-optimistic-layer.md).
  Read: [`useOptimistic`](https://react.dev/reference/react/useOptimistic), [Apollo: optimistic mutation results](https://www.apollographql.com/docs/react/performance/optimistic-ui).

- **Testing with RNTL's user-event and MSW, and what the flow tests found.** `userEvent.setup()` and `await user.press(...)` simulate a press the way the platform does (pressIn, delay, pressOut), where `fireEvent.press` only calls the handler; queries by role and name (`getByRole('button', { name })`) test what a screen reader would find, so an accessibility bug is a test failure. MSW answers at the network level, so the real link chain, cache, queue and routes run; [cartServer.ts](../apps/mobile/src/test/msw/cartServer.ts) is a fake server with the real one's idempotency rule, which lets a test check "the server cart matches" and "no key was applied twice". Hard-won details: React 19's `act` must be **awaited**, or the update is not flushed; the router's test renderer turns on fake timers, and a request does not finish while time is faked, so a flow test goes back to real timers after the app is up; and a clock taken once (`now = Date.now`) stays on the fake clock after that. Wiring the queue to the UI found **three bugs in the replayer** that its unit tests (3.9) had missed, because each needed the real wiring: an empty replay left it "busy" forever, a subscriber calling `replay()` from inside a queue update recursed without end, and the frozen clock. Each has its own regression test now. The lesson to say out loud: a unit-tested state machine can still be wrong at its seams, and flow tests are where they show.
  Here: [shoppingFlows.test.tsx](../apps/mobile/src/__tests__/shoppingFlows.test.tsx), [CartScreen.test.tsx](../apps/mobile/src/features/cart/__tests__/CartScreen.test.tsx), [replayer.test.ts](../apps/mobile/src/features/cart/__tests__/replayer.test.ts).
  Read: [RNTL: User Event](https://callstack.github.io/react-native-testing-library/docs/api/events/user-event), [MSW](https://mswjs.io/docs/).

- **Search state in the URL, and an A/B test that measures what users saw.** The search screen keeps its state in route params, in one canonical form (ADR 0010), so a link, the back button and a restart all reproduce a search. A feature flag assigns a user to a variant by hashing `salt:flag:userId`, so the same user gets the same variant offline and on every launch with nothing stored. The exposure event is logged when the variant is **visible**, not when the flag is read: `search_layout` is read on the search screen but exposed when the result list mounts, because a user who opened search and left never saw either layout, and counting them would dilute the measured effect. Be ready to name the known weakness: the user id can change at sign-in (ADR 0012).
  Here: [SearchResults.tsx](../apps/mobile/src/features/search/components/SearchResults.tsx), [useFlag.ts](../apps/mobile/src/flags/useFlag.ts), [FlagDebugPanel.tsx](../apps/mobile/src/features/settings/components/FlagDebugPanel.tsx); [ADR 0010](adr/0010-search-url-params-and-canonical-search-input.md), [ADR 0012](adr/0012-feature-flags-assignment-and-exposure.md).
